# Ollama 模型管理与自定义 - GGUF 深度解析与量化选型

> **版本基线**：Ollama 0.17.x
> **本章定位**：理解 GGUF 格式与量化原理，掌握 Agent 场景下的量化选型——"为什么选这个量化级别"

## 一、GGUF 是什么

先打个比方：**GGUF 就像模型的"压缩打包文件"**——一个文件里装好了模型的大脑（权重）、说明书（超参数）、字典（分词器）和证件（元数据），拿到就能用，不用再四处找配套文件。

GGUF（GPT-Generated Unified Format）是 llama.cpp 生态的**统一模型文件格式**。一个 GGUF 文件内打包了：

- **模型权重**：量化后的张量数据；
- **超参数**：层数、头数、上下文长度等架构信息；
- **分词器（Tokenizer）**：词汇表与分词规则；
- **元数据**：作者、许可、训练信息等。

这意味着**一个 GGUF 文件就是一个自包含的模型**，不需要额外的 config.json、tokenizer.json 等散装文件。这也是 Ollama 下载模型"一个文件搞定"的根本原因。

```
GGUF 文件内部结构（简化）
┌─────────────────────────────┐
│ Header: magic "GGUF" + 版本  │
├─────────────────────────────┤
│ Metadata KV: 超参数/分词器/元数据│
├─────────────────────────────┤
│ Tensor 数据: 各层权重(已量化)   │
└─────────────────────────────┘
```

### 1.1 为什么 GGUF 是事实标准

GGUF 由 llama.cpp 项目维护，整个本地推理生态（Ollama、LM Studio、Jan、llama.cpp 直接调用）都以它为标准格式。**在 Hugging Face 上找本地模型，认准 GGUF 后缀**（如 `qwen3-8b-Q4_K_M.gguf`）。

Ollama 的模型库下载后本质就是 GGUF 文件，只是由 Ollama 统一管理、无需手动处理。反过来，你也可以把任意 GGUF 文件导入 Ollama（见 [3.1 自定义导入模型](./1.%20自定义导入模型.md)）。

## 二、量化（Quantization）原理

### 2.1 为什么要量化

大模型权重默认是 16 位浮点数（FP16），8B 模型 FP16 约 **16 GB**，多数消费级显卡装不下。量化（Quantization）把权重从 16 位压缩到 8 位、5 位、4 位甚至更低，**体积成倍缩小，换来可接受的精度损失**。

### 2.2 常见量化级别（bytes/param）

| 量化级别 | 字节/参数 | 8B 模型体积(约) | 相对 FP16 | 质量损失 |
|---|---|---|---|---|
| f16 | 2.0 | 16 GB | 100% | 无损（基准） |
| q8_0 | 1.06 | 8.5 GB | 53% | 极轻微 |
| q6_K | 0.81 | 6.5 GB | 41% | 轻微 |
| q5_K_M | 0.68 | 5.4 GB | 34% | 较小 |
| **q4_K_M** | 0.57 | **4.5 GB** | 28% | **可接受（社区主流选择）** |
| q4_0 | 0.56 | 4.5 GB | 28% | 可接受（略逊于 K_M） |
| q3_K_M | 0.41 | 3.3 GB | 21% | 明显 |
| q2_K | 0.34 | 2.7 GB | 17% | 严重（不推荐生产使用） |

> K_M / K_S / K_M 后缀：llama.cpp 的 K-quant 方法对**注意力层用更高精度、其他层用更低精度**做混合量化，同等体积下比旧式 q4_0 质量更好。**同体积下优先选带 K 的版本**。

## 三、Agent 场景下的量化选型

聊天场景下 q4_K_M 是默认好选择；但 **Agent 场景的量化决策逻辑不同**——工具调用的参数要精确结构化输出，代码要保真，量化损失会被放大。

### 3.1 三个决策原则

1. **代码与结构化输出 → 高精度**：工具调用的函数名、参数名、代码语法都是"要么对要么错"的任务，量化损失直接导致 JSON 格式错误、函数名拼错。**做 Agent 后端的模型，量化尽量不低于 q5_K_M，显存允许则 q8_0**。
2. **显存决定上限，量化决定质量**：显存装不下 q8_0 时，降量化（q8_0 → q4_K_M）优于降参数规模（14B → 7B）——14B 的 q4_K_M 通常比 7B 的 q8_0 更聪明，但工具调用稳定性两者相当，需实测。
3. **推理型模型（R1 类）谨慎降级**：推理模型的长思维链对数值精度更敏感，建议至少 q4_K_M 起步，不要低于 q3。

### 3.2 场景速查表

| 场景 | 推荐量化 | 理由 |
|---|---|---|
| 通用对话/聊天 | q4_K_M | 质量/体积平衡点 |
| Agent 后端（工具调用） | **q5_K_M ~ q8_0** | 结构化输出保真 |
| 代码补全/生成 | q8_0（显存允许） | 语法精确性要求高 |
| RAG 生成端 | q4_K_M ~ q5_K_M | 生成质量要求中等 |
| 低显存（4GB 以下） | q4_K_M（接受折损） | 唯一能跑的选择 |
| 嵌入模型（bge-m3 等） | 原版即可 | 嵌入模型量化需谨慎，一般用原版 |

### 3.3 在 Ollama 中指定量化

```bash
# 拉取指定量化版本
ollama pull qwen3:8b-q8_0
ollama pull qwen3:8b-q4_K_M

# 查看某个模型的所有可用 tag
ollama show qwen3:8b --tags   # 或访问 https://ollama.com/library/qwen3/tags
```

> 注意：不是所有模型都发布了全量化版本。`ollama show <模型> --tags` 之前，可以先在 [ollama.com/library](https://ollama.com/library) 模型主页的 Tags 页确认。

### 3.4 验证当前模型的量化级别

```bash
ollama show qwen3:8b
```

输出中的 `Quantization` 字段会显示实际量化（如 `Q4_K_M`）。加载后 `ollama ps` 还能看到实际显存占用，与理论值对比即可判断量化是否生效。

## 四、量化与上下文、工具调用的联动

选量化不是孤立决策，它与另外两个变量联动：

1. **上下文长度（num_ctx）**：上下文越长，KV cache 越大，留给权重的显存越少。长上下文 Agent 场景下，可能需要"q4_K_M + 长上下文"而不是"q8_0 + 短上下文"。
2. **KV cache 量化**：`OLLAMA_KV_CACHE_TYPE=q8_0` 可进一步压缩缓存（见 [C2.5](../C2/5.%20GPU-CPU%20混合推理配置.md)），把省下的显存还给权重精度。

**实践建议**：在目标硬件上做一次「同模型不同量化」的 tool calling 实测（脚本见第8章），用 20 个工具调用请求对比成功率，再决定最终量化——比任何理论表格都可靠。

## 本章小结

- GGUF 是 llama.cpp 生态的统一模型格式，一个文件自包含；
- 量化 = 用精度换体积，q4_K_M 是聊天场景的平衡点；
- **Agent 场景工具调用对量化敏感，推荐 q5_K_M ~ q8_0**；
- 量化、上下文、KV cache 三者联动，最终以本地实测为准。
