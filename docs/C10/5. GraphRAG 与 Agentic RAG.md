# GraphRAG 与 Agentic RAG

> **版本基线**：概念与实现思路（2026 年 9 月），示例基于本地 Ollama 可复现
> **章节定位**：基础 RAG 的进阶方向——GraphRAG（知识图谱增强）与 Agentic RAG（检索智能化），两者均可纯本地实现

## 一、基础 RAG 的两个短板

基础 RAG（第 2~4 节）存在两个结构性问题：

1. **多跳问题答不了**："A 公司的创始人创办的 B 公司总部在哪？"——答案分散在多个文档片段，向量检索很难一步命中；
2. **检索策略死板**：无论什么问题都"检索一次、拼进去、生成"，遇到复杂问题不会调整策略。

GraphRAG 解决第一个问题，Agentic RAG 解决第二个。

## 二、GraphRAG：用知识图谱组织知识

### 2.1 核心思想

GraphRAG（微软提出）在向量检索之外增加**知识图谱**层：

```
文档 ──实体抽取──► (实体)─┬─关系──► (关系)
                  └─属性──► (属性)
                    ↓
              图结构存储 + 社区检测(Community)
                    ↓
  查询时: 向量检索(精确命中) + 图检索(多跳推理) + 社区摘要(全局理解)
```

- **向量检索**负责"找相似片段"；
- **图检索**负责"沿着实体关系跳转"——多跳问题在这里解决；
- **社区摘要**负责"全局概览"——"这份文档讲了哪几件事"类问题。

### 2.2 本地实现方式

| 方案 | 说明 | 本地可行性 |
|---|---|---|
| **LightRAG** | 轻量 GraphRAG 实现，纯 Python | ✅ 完全本地，Ollama 当 LLM+Embedding |
| **MS GraphRAG**（官方） | 微软官方实现，功能全但重 | ✅ 可本地（LLM 配 Ollama），资源开销大 |
| **手动构建** | 用 Ollama 抽取实体/关系存入 Neo4j | ✅ 灵活，工程量自控 |

```python
from lightrag import LightRAG, QueryParam
from lightrag.llm.ollama import ollama_model_complete, ollama_embed
from lightrag.utils import EmbeddingFunc

rag = LightRAG(
    working_dir="./graph_data",
    llm_model_func=ollama_model_complete,      # LLM: Ollama
    embedding_func=EmbeddingFunc(
        embedding_dim=1024,
        max_token_size=8192,
        func=ollama_embed,                     # 嵌入: Ollama(bge-m3)
    ),
    llm_model_name="qwen3:8b",
)

rag.insert(open("document.txt").read())        # 建图
print(rag.query("A 公司的创始人创办了哪家公司?",
                param=QueryParam(mode="hybrid")))  # 混合检索
```

### 2.3 何时该用 GraphRAG

| 场景 | 基础 RAG | GraphRAG |
|---|---|---|
| 问答类（单片段可答） | ✅ 够用 | 杀鸡用牛刀 |
| 多跳推理（跨片段） | ❌ 常失败 | ✅ 擅长 |
| 全局概览/主题总结 | 弱 | ✅ 社区摘要 |
| 数据量小（<100 文档） | ✅ | 建图成本不值 |
| 数据量大且关系密集 | 检索噪声大 | ✅ 结构化优势 |

## 三、Agentic RAG：让 Agent 决定怎么检索

### 3.1 核心思想

Agentic RAG 把检索从"固定流水线"变成"Agent 决策"：

```
用户提问
   │
   ▼
┌─────────────────────────────────────────┐
│ Agent(本地模型)                           │
│  思考: 这个问题需要检索吗? 查什么? 查几次? │
│  ├─► 调用检索工具(向量库/网络/数据库)      │
│  ├─► 评估结果够不够 → 不够就再查/换策略    │
│  └─► 够了 → 基于全部资料生成最终答案       │
└─────────────────────────────────────────┘
```

### 3.2 三种典型模式

| 模式 | 流程 | 适用 |
|---|---|---|
| **单轮检索** | 查一次 → 回答 | 简单事实问题 |
| **多轮检索（iterative）** | 查 → 不满足 → 换关键词/换库再查 → 回答 | 复杂、需多源核实 |
| **多工具检索（agentic）** | Agent 自主选择：向量库 / Web 搜索 / SQL / 计算器 | 开放域问题 |

### 3.3 本地实现：把检索变成工具

结合第 8 章的 Agent 框架，把"检索"注册为一个工具即可：

```python
TOOLS = [{"type": "function", "function": {
    "name": "search_knowledge_base",
    "description": "在本地知识库中检索与问题相关的文档片段",
    "parameters": {"type": "object",
                   "properties": {"query": {"type": "string"}},
                   "required": ["query"]}}}]

def search_knowledge_base(query: str) -> str:
    """向量检索: 问题 → 嵌入 → Top-K 相似片段"""
    vec = embed_model.get_text_embedding(query)
    hits = vector_db.query(vec, top_k=3)
    return "\n---\n".join(h.text for h in hits)
```

然后把 `search_knowledge_base` 加入第 8 章 `mini_agent.py` 的 `FUNCS`/`TOOLS`——**模型就会自主决定"要不要查、查什么、查完够不够"**。一个 120 行的本地 Agentic RAG 就完成了。

## 四、选择路线图

```
你的需求是什么?
├─ 单片段问答、快速落地 ──────────► 基础 RAG(第2~4节) + 调优
├─ 多跳推理、全局概览、数据量大 ────► GraphRAG(LightRAG 起步)
├─ 复杂开放域、需要检索决策 ────────► Agentic RAG(第8章框架 + 检索工具)
└─ 都要 ─────────────────────────► Agentic RAG + GraphRAG 混合(工程量大, 量力而行)
```

**进阶建议**：先用基础 RAG 跑通并量化瓶颈（哪些问题答错），再决定上 GraphRAG 还是 Agentic RAG——**用数据说话，而不是追技术时髦**。

## 本章小结

- 基础 RAG 两大短板：多跳问题、死板策略；
- **GraphRAG**：知识图谱 + 社区摘要，解决多跳与全局理解（LightRAG 可纯本地）；
- **Agentic RAG**：检索工具化，让本地模型自主决策检索策略（第8章框架 + 一个工具函数即可实现）；
- 选择路线：先量化瓶颈，再选进阶方案。
