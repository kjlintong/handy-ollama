# 本地模型资源调度

> **版本基线**：Ollama 0.17.x（环境变量行为以官方 faq 为准）
> **章节定位**：多模型/多 Agent 场景的显存规划与并发策略——让有限的本地硬件跑起更多模型
> **前置**：[C2.5 GPU/CPU 混合推理配置](../C2/5.%20GPU-CPU%20混合推理配置.md)

## 一、问题的提出

多 Agent 场景（CrewAI / LangGraph / 多个 Harness 会话）意味着**多个模型要同时驻留内存**：对话模型、嵌入模型、推理模型……显存/内存是硬约束，规划不当就会出现"换模型卡顿、OOM、排队"。

先看两个基本事实：

- 8B 模型 Q4_K_M 量化：权重约 **4.5 GB**，加上 KV cache（上下文越长越大）与运行时开销，实际占用 6~8 GB；
- 嵌入模型（bge-m3）：约 **1.2 GB**，但一般只需驻留一次。

## 二、Ollama 的并发加载机制

| 环境变量 | 默认 | 作用 | 多 Agent 建议 |
|---|---|---|---|
| `OLLAMA_MAX_LOADED_MODELS` | 3 × GPU 数（CPU 为 3） | 最多同时驻留几个模型 | 按显存实测调 |
| `OLLAMA_NUM_PARALLEL` | 1 | 单模型并行处理请求数 | 2~4（视显存） |
| `OLLAMA_KEEP_ALIVE` | 5m | 模型处理完驻留多久 | 24h（频繁用）/ 0（省显存） |
| `OLLAMA_MAX_QUEUE` | 512 | 请求队列上限 | 默认即可 |
| `OLLAMA_FLASH_ATTENTION` | 自动 | 长上下文省显存 | 1 |
| `OLLAMA_KV_CACHE_TYPE` | f16 | KV cache 量化 | q8_0（省显存） |

> 配置方法见 [C2.5](../C2/5.%20GPU-CPU%20混合推理配置.md)；这些变量在 `ollama serve` 启动前设置。

## 三、显存规划方法（三步法）

**第 1 步：估算模型占用**

```
总占用 ≈ 权重体积 + KV cache + 运行开销
权重体积: 8B@Q4_K_M ≈ 4.5GB, 8B@Q8_0 ≈ 8.5GB, 14B@Q4_K_M ≈ 8GB
KV cache: 与上下文长度成正比(32K 上下文约额外 2~4GB, 视模型)
经验余量: 预留 20%
```

**第 2 步：规划模型组合**

示例：12 GB 显存 + 16 GB 内存的机器，跑"RAG + 对话"双模型：

| 模型 | 量化 | 权重 | 上下文 | 预计占用 |
|---|---|---|---|---|
| qwen3:8b（对话） | Q4_K_M | 4.5 GB | 32K | ~7 GB |
| bge-m3（嵌入） | 原版 | 1.2 GB | — | ~1.5 GB |
| **合计** | | | | **~8.5 GB** ✅ 放得下 |

> 放不下时的降级顺序：**降 KV cache 精度 → 缩短上下文 → 降量化 → 换小模型**（按成本从低到高）。

**第 3 步：验证**

```bash
ollama ps   # 查看已驻留模型与显存占用
```

## 四、多 Agent 场景的调度策略

### 4.1 串行优先（最省资源）

多 Agent 流程大多可以串行：同一时间只驻留一个模型，`OLLAMA_KEEP_ALIVE` 调大减少反复加载：

```
研究 Agent(加载qwen3:8b) → 写完卸载? → 写作 Agent(复用同一模型)
```

同一模型被多个 Agent 复用时，**Ollama 只加载一份**，天然省显存。

### 4.2 并行按需（快但吃显存）

需要同时驻留多个模型时：

```bash
export OLLAMA_MAX_LOADED_MODELS=3
export OLLAMA_NUM_PARALLEL=2
export OLLAMA_KV_CACHE_TYPE=q8_0
export OLLAMA_FLASH_ATTENTION=1
```

规则：**总占用 ≤ 显存的 80%**，剩余留给系统与突发。

### 4.3 显存告急时的三板斧

1. `keep_alive: 0`——每个请求处理完立即卸载模型（慢但稳）：
   ```bash
   curl http://localhost:11434/api/chat -d '{"model":"qwen3:8b","messages":[...],"keep_alive":0}'
   ```
2. 缩短上下文：`num_ctx` 从 64K 降到 16K（KV cache 显著减小）；
3. 换小模型：8B → 3B/4B（功能折损，但保住流程）。

### 4.4 嵌入模型的特殊处理

嵌入模型（bge-m3）建议**常驻**（`OLLAMA_KEEP_ALIVE=-1` 或单独拉高），因为 RAG 场景会频繁调用嵌入；对话模型按需加载即可。

## 五、监控与排障

```bash
# 查看驻留模型与资源
ollama ps

# 查看加载日志(确认 GPU/CPU 分配)
tail -f ~/.ollama/logs/server.log   # Linux/macOS
# Windows: 任务栏 Ollama 图标 → View Logs

# 常见问题
# 1. 请求 503: 队列满 → 调大 OLLAMA_MAX_QUEUE 或减少并发
# 2. 换模型特别慢: 反复加载卸载 → 调大 KEEP_ALIVE
# 3. OOM 崩溃: 减模型数量/量化/上下文
```

更多排查见 [living-docs/troubleshooting.md](../../living-docs/troubleshooting.md)。

## 本章小结

- 多模型驻留是显存规划问题：**权重 + KV cache + 余量**三步估算；
- 并发四变量：`MAX_LOADED_MODELS` / `NUM_PARALLEL` / `KEEP_ALIVE` / `KV_CACHE_TYPE`；
- 策略选择：串行优先省资源、并行按需提速度、告急三板斧兜底；
- 嵌入模型常驻、对话模型按需，`ollama ps` 随时验证。
