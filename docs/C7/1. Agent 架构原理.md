# Agent 架构原理

> **版本基线**：不依赖具体版本，讲通用原理
> **章节定位**：用最小篇幅讲清 Agent 的核心机制（ReAct / Planning / Tool Use），重点是回答——**为什么本地模型在 Agent 场景下容易出问题**。本章不造框架，目的让读者"看懂轮子怎么转"，下一章再动手造一个。
> **边界铁律**：本章只讲原理与本地模型的适配问题，不教任何 Harness 的操作。

## 一、Agent 是什么

> **Agent = 模型 + 工具 + 循环**

与传统"一问一答"的聊天模型不同，Agent 是一个**自主执行任务的过程**：

```
用户给目标 → 模型思考 → 决定行动(调用工具/直接回答) → 执行
    ↑                                                    │
    └──────────── 观察结果 → 继续思考 ←──────────────────┘
```

聊天模型是"一次性回答"，Agent 是"循环直到任务完成"。这个循环有三个核心机制：**ReAct、Planning、Tool Use**。

## 二、ReAct：推理与行动的交替

ReAct（Reasoning + Acting）是 Agent 最基础的循环模式，由 Yao et al. 在 2022 年提出。它的核心思想：**模型交替进行"思考（Reason）"和"行动（Act）"，把外部观察（Observation）纳入下一轮思考**。

```
Thought: 用户问北京天气, 我需要天气数据 → Reason
Action: get_weather(city="北京")          → Act
Observation: 北京: 晴, 32°C               → 工具返回
Thought: 有了天气数据, 可以回答了           → Reason
Answer: 北京今天晴, 32°C                   → 最终输出
```

在实现层面，ReAct 循环的每一步都通过**对话消息**传递：

| 消息角色 | 内容 | 对应 ReAct 环节 |
|---|---|---|
| `user` | 任务描述 | 目标 |
| `assistant` + `tool_calls` | 模型决定调用工具 | Action |
| `tool` | 工具执行结果 | Observation |
| `assistant`（无 tool_calls） | 最终回答 | Answer |

这就是第 4 章 Tool Calling API 与第 5 章 MCP 调用链的完整意义——**它们就是 ReAct 循环的通信协议**。上一章 `ollama_mcp_agent.py` 里那个 while 循环，就是 ReAct 的最小实现。

### 2.1 一次真实的多轮 ReAct 循环（实测日志逐行解读）

理论讲完了，看一段**真实运行日志**（本书环境：Ollama 0.17.7 + qwen3:8b-64k，完整代码见[第8章](../C8/1.%20轻量级%20Agent%20实现.md)的 mini_agent.py，任务："帮我查一下北京天气，然后计算 23\*17+9 等于多少"）：

```
===== 第 1 轮 =====
[工具] get_weather{"city": "北京"} -> 北京: 晴, 32°C        ← Action + Observation
[工具] calculator{"expr": "23*17+9"} -> 400                ← Action + Observation
===== 第 2 轮 =====
[模型] 北京今天天气晴，温度32°C。
23*17+9 的计算结果是 400。                                  ← Answer
```

对照 ReAct 环节逐行解读：

| 日志行 | 环节 | 说明 |
|---|---|---|
| `[工具] get_weather{"city": "北京"}` | Action | 模型**没有直接回答**，而是决定调用天气工具，参数完全正确 |
| `-> 北京: 晴, 32°C` | Observation | 工具真实执行，结果回到模型上下文 |
| `[工具] calculator{"expr": "23*17+9"}` | Action | **同一轮并行发起第二个工具调用**（两个子任务互不依赖） |
| `-> 400` | Observation | 第二个工具结果回传 |
| `[模型] 北京今天天气晴...` | Answer | 模型综合全部工具结果，给出最终回答，循环结束 |

三个值得注意的细节：

1. **模型自己"拆任务"**：把一句话任务拆成"查天气"和"算算术"两个子任务，并识别出它们互不依赖，一次性并行调用；
2. **参数零误差**：`{"city": "北京"}`、`{"expr": "23*17+9"}` 与工具 schema 完全一致——这是第 8 章代码里 `TOOLS` 描述写得清楚的结果；
3. **循环只跑了两轮**：第 1 轮行动、第 2 轮收尾。如果模型对工具结果不满意，它会继续循环（最多 MAX_ROUNDS 轮）。

再看一个"出错后自我修正"的例子（同一环境，任务："读取 README.md 的标题行"）：

```
===== 第 1 轮 =====
[工具] read_file{"path": "README.md"} -> 读取失败: [Errno 2] No such file or directory
===== 第 2 轮 =====
[模型] README.md 文件未找到，请确认文件是否存在或检查路径是否正确……
```

模型在错误信息（Observation）的基础上**如实报告失败**，而不是幻觉编造文件内容——这正是"把错误回传给模型"这一容错设计的价值（详见 5.1）。

## 三、Planning：把大任务拆成小步骤

复杂任务（"帮我调研并写一份报告"）无法一步完成，需要**规划**。常见规划方式：

1. **隐式规划（模型自动）**：ReAct 循环中模型自己决定下一步——最简单，但容易走偏；
2. **显式规划（Plan-and-Execute）**：先让模型输出步骤清单，再逐步执行：
   ```
   用户: 写一份本地大模型部署方案
   模型: 计划: 1. 调研硬件需求 2. 选择模型 3. 写部署步骤 4. 输出报告
   然后: 逐步执行, 每步完成后更新计划
   ```
3. **任务分解（Task Decomposition）**：把任务拆成子任务，必要时分给多个子 Agent（多 Agent 协作见[第11章](../C11)）。

### 3.1 Plan-and-Execute 的最小实现

显式规划的实现并不复杂：**先用一次模型调用生成计划，再循环执行计划中的每一步**。下面是一个 30 行的最小骨架（完整可运行代码见 `notebook/C8/plan_execute.py`）：

```python
def make_plan(client, task: str) -> list[str]:
    """第一步: 让模型把任务拆成步骤清单"""
    resp = client.chat(model=MODEL, messages=[
        {"role": "system", "content": "把任务拆成 3~5 个可执行的步骤, 每行一个, 不要多余解释。"},
        {"role": "user", "content": task},
    ])
    steps = [line.strip() for line in resp.message.content.splitlines() if line.strip()]
    return steps

def execute_step(client, step: str) -> str:
    """第二步: 逐步执行(这里简化为直接问答, 实际可接工具调用)"""
    resp = client.chat(model=MODEL, messages=[{"role": "user", "content": step}])
    return resp.message.content

def run(task: str) -> None:
    plan = make_plan(client, task)          # 1. 规划
    print("计划:", plan)
    results = []
    for step in plan:                       # 2. 逐步执行
        print(f"执行: {step}")
        results.append(execute_step(client, step))
    # 3. 汇总
    summary = client.chat(model=MODEL, messages=[
        {"role": "user", "content": f"基于以下分步结果, 输出最终答案:\n{chr(10).join(results)}"}])
    print("最终答案:", summary.message.content)

run("调研并介绍 3 个本地大模型工具")         # 演示
```

这个骨架展示了 Plan-and-Execute 的三段式：**规划 → 逐步执行 → 汇总**。把它与第 8 章的工具调用结合，就得到"先规划、后带工具执行"的完整 Agent。注意逐步执行时每步结果要**保存并汇总**，而不是让模型凭记忆——本地模型跨步骤"忘事"很常见（见 5.2）。

**本地模型的规划能力特征**：8B 级模型能做 3~5 步的简单规划，但长链路（10+ 步）容易"走失"——忘了最初目标、重复执行某一步、计划与执行脱节。应对策略：

- **把目标写进系统提示词**，每轮都可见；
- **限制单次任务的步骤数**（MAX_ROUNDS）；
- **复杂任务交给更强的模型**或云端模型（混合策略，见[第9章](../C9)）。

## 四、Tool Use：Agent 的"手"

模型本身不会查天气、读文件、跑代码——这些能力来自工具。工具调用的关键机制（详见[第4章](../C4/3.%20Tool%20Calling%20API.md)）：

```
模型输入: 工具描述(JSON Schema) + 当前对话
模型输出: {tool_calls: [{name: "get_weather", arguments: {city: "北京"}}]}
程序执行: 真正调用 get_weather
结果回传: role="tool" 消息
```

**工具描述就是模型的世界观**——它只能通过工具描述"知道"世界有什么能力。因此：

- 工具描述要准确、简洁、可区分；
- 工具数量要克制（本地模型尤其敏感，见[第5章](../C5/4.%20常用%20MCP%20Server%20与%20Ollama%20配合.md)）；
- 工具执行失败时，**把错误信息回传给模型**，它往往能自我修正（换参数、换工具）。

## 五、为什么本地模型在 Agent 场景容易出问题

这是本章的核心问题。同样的 Agent 代码，换成本地模型后经常"失灵"，根本原因有三类：

### 5.1 能力维度：工具调用不稳定

| 问题 | 表现 | 根因 |
|---|---|---|
| 该调用时不调用 | 直接说"我不知道" | 模型没理解工具用途（描述问题或模型能力弱） |
| 参数错误 | 城市名写成"北京市北京" | 小模型对 JSON Schema 遵循能力弱 |
| 格式损坏 | arguments 不是合法 JSON | 量化损失 + 小模型约束力弱 |
| 幻觉工具 | 调用不存在的函数 | 模型"编造"工具 |

**对策**：选工具调用能力强的模型家族（Qwen3、Llama 3.1+）；量化别太低（见[第3章](../C3/4.%20GGUF%20深度解析与量化选型.md)）；代码里做重试与容错。

### 5.2 上下文维度：容易"失忆"与"走偏"

- Agent 循环中，每轮都要回传全部历史（含工具结果），**上下文快速膨胀**——8K 上下文很快耗尽；
- 上下文一满，**早期的任务目标、关键约束被截断**，模型开始"忘记目标"；
- 工具结果很长（大段日志、网页正文）时尤其严重。

**对策**：用长上下文模型（如 qwen3:8b-64k）并合理设置 `num_ctx`；工具输出截断；把关键目标固定在系统提示词里。

### 5.3 性能维度：慢 + 并发受限

- 本地 8B 模型推理速度约 20~60 token/s（视硬件），一轮 ReAct 循环（含思考）可能耗时 10 秒以上；
- 多步任务 = 多轮循环 = **分钟级等待**，体验远不如云端；
- 并发受限（默认单并发），多个 Agent 同时跑会排队（见[第11章](../C11)资源调度）。

**对策**：任务拆小、减少循环轮数；能一次调用多个工具就并行（模型支持并行 tool_calls）；预算足够的场景用混合策略。

### 5.4 一张图总结

```
云端模型:   理解力强 + 遵循力强 + 速度快 → Agent 流畅
本地模型:   理解力够 + 遵循力弱 + 速度慢 → Agent 可用但需工程化
解决思路:  选对模型(能力) + 精简工具(遵循) + 控制上下文(记忆) + 容错重试(健壮)
```

## 六、什么时候该用本地模型做 Agent

本地模型不是万能的，但在以下场景**明确优于云端**：

| 场景 | 理由 |
|---|---|
| 隐私敏感（代码库、医疗数据） | 数据不出本机 |
| 离线/内网环境 | 无网络依赖 |
| 成本敏感的高频任务 | 免费、无限量 |
| 延迟不敏感的后台批处理 | 可接受分钟级耗时 |
| 模型能力已够用的常规任务 | 8B 模型可胜任简单工具调用与问答 |

## 本章小结

- Agent = 模型 + 工具 + 循环；三大机制：**ReAct（思考行动交替）、Planning（任务拆解）、Tool Use（工具调用）**；
- ReAct 循环通过消息角色传递：user 目标 / assistant+tool_calls 行动 / tool 观察 / assistant 回答；
- 本地模型三大短板：**工具调用不稳定、上下文易失忆、推理慢**——都有工程化对策；
- 选型原则：能力够用 + 隐私/离线/成本敏感时，本地模型是正确选择。
